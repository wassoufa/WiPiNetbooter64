# Native runtime comparison and diagnostic capture

Use [the current handoff](ai-handoff.md) to identify the candidate and [the roadmap](roadmap.md) for gates. This plan is not a record of completed emulator/hardware tests. Copy [the blank result/bug template](templates/runtime-test-result.md) per run; keep raw material private and publish only reviewed, redacted findings.

## Before a run

1. Assign a run ID and case IDs, timestamp/timezone and operator. Record host/emulator/Pi clock offsets if logs use different clocks. Hash the source checkpoint, base ROM, configured runtime ROM and synthetic configuration separately. Retain the matching debug ELF, manifest, builder ID, compiler and packages. Name games/targets with test IDs in public results; retain private mappings outside the checkout.
2. Record the environment: emulator version/build, BIOS identity/hash where lawfully available, renderer/backend and input mappings; or Naomi/NetDIMM revisions, physical JVS setup, 31 kHz CRT mode and launch source (OSM/phone). Record only redacted configuration differences publicly. Do not treat repository defaults as installed settings.
3. Choose expected outcomes and repetitions before testing. Set a bounded soak duration/cycle count and define what will stop a run (crash, wrong selection, unexpected write/reset, unresponsive controls, corrupt settings/SRAM or repeated memory growth). Stop on a material failure, preserve evidence and review before resuming. Never interrupt a live transfer to manufacture a failure.
4. Confirm capture methods work, available storage, and the log overwrite behavior below. Keep debug/verbose flags, catalog/configuration, warm/cold state and timing start/end definitions consistent in comparisons. A debug overlay may itself cost time; label that run separately from a normal performance run.

## Stage E: isolated emulator preparation and baseline

**E0 — readiness.** Own-board BIOS acquisition, the isolated synthetic fixture and a supported interpreter-only Flycast setup are now available. The [dated result](results/2026-11-13-native-emulator.md) records actual rendering/navigation observations; the [build recipe](flycast-local-build.md) owns pinned source, dependency/tool identities, build-only patches, failed JIT attempts and the successful interpreter fallback. The Homebrew cask's Gatekeeper issue was not bypassed; official source was built outside the repository. Firmware and emulator persistence remain private. Native cabinet acceptance is separate.

The stock [Flycast v2.7 raw Naomi ROM path requires `naomi.zip`](https://github.com/flyinghead/flycast/blob/5aa091fde632fb332c8d8c34e280d62dc951954c/core/hw/naomi/naomi_cart.cpp#L458-L465). It also lacks this menu's host-message bridge: [`loadDecryptedRom()` constructs `DecryptedCartridge`](https://github.com/flyinghead/flycast/blob/5aa091fde632fb332c8d8c34e280d62dc951954c/core/hw/naomi/naomi_cart.cpp#L609), which [inherits the ordinary register handler](https://github.com/flyinghead/flycast/blob/5aa091fde632fb332c8d8c34e280d62dc951954c/core/hw/naomi/naomi_cart.h#L109). That handler [returns fixed DIMM values](https://github.com/flyinghead/flycast/blob/5aa091fde632fb332c8d8c34e280d62dc951954c/core/hw/naomi/naomi_cart.cpp#L921-L941) and [ignores register writes](https://github.com/flyinghead/flycast/blob/5aa091fde632fb332c8d8c34e280d62dc951954c/core/hw/naomi/naomi_cart.cpp#L985-L1006). The [separate commercial GD-title NetDimm path](https://github.com/flyinghead/flycast/blob/5aa091fde632fb332c8d8c34e280d62dc951954c/core/hw/naomi/naomi_cart.cpp#L277-L284) is not a raw-ROM bridge. E3 therefore remains unsupported on this route; no adapter has been implemented. Scope real NetDIMM round trips explicitly rather than treating an expected emulator timeout as a renderer failure or a pass.

**E1 — fixture.** The ignored build output is a bare menu ROM. The [offline generator and proof commands](../native/README.md#offline-emulator-fixture) now prepare a synthetic 64-byte configuration and 26 bounded 136-byte game records at `0x0D000000`, using the existing serializer layout and ROM section helper. The fixture includes invented IDs/titles, one-character and 127-character titles, and enough records to scroll. SRAM is disabled and sound muted; selection/count/pointers/serials/calibration and absent font bounds are coherent. Four focused offline checks passed on 2026-11-13. The manifest and checksums under ignored `native/out/emulator/` record the fixture, base and configured-ROM identities; [the handoff](ai-handoff.md#candidate-artifact-and-reproducibility-record) indexes the current hashes. No emulator behavior is established by this check. Do not invoke `netdimm_menu` merely to obtain a configured ROM: it also touches cabinet paths and starts network transfers. Do not copy the real `/var/log/menudump.bin` or cabinet catalog into public fixtures.

**E2 — render/navigation.** Verify boot to list, text/fonts/long titles, focus/highlight, scrolling at both ends, repeated Up/Down, held/released controls and a stable idle screen. Capture a screenshot/video at known case IDs and include emulator console output. Confirm that browsing alone sends no selection/launch request. Check orientation/fallback fonts only with supported synthetic configurations; record unsupported cases.

**E3 — protocol-dependent behavior.** First establish whether a supported isolated message bridge can receive selection and return settings/configuration ACK/data. Without it, short Start or long Start may enter an expected communications timeout; that is not a successful settings/launch test or necessarily a renderer regression. With a verified bridge, record short Start press/release selecting the correct ID once; long Start opening settings without a launch; Back/cancel returning to the prior selection; both save-and-exit paths; and repeated settings entry/change/exit. Keep malformed/truncated packets, delayed/no ACK and synthetic SRAM failures in isolated fixtures. Existing C fixtures cover specific ownership paths, not an emulator's whole menu. Mark each unsupported round trip unverified with the bridge limitation.

**E4 — bounded repetition.** Repeat navigation and supported settings cycles, recording duration/cycle count, freezes, frame observations and memory measurements where available. Save startup and end captures with identical measurement conditions. Preserve crashes/exceptions and emulator error codes, PC/registers/backtrace if exposed. Resolve addresses only against the matching `naomi.elf`; do not guess a source line or offset from another build.

Exit record: rendering/navigation outcomes, bridge-supported protocol outcomes, unknowns and bug references. Emulator results cannot establish physical JVS, real NetDIMM transfer/gameplay, battery SRAM persistence, CRT sync/overscan or Single Boot. Prepare the concrete hardware comparison only after emulator failures are understood; an unsupported emulator feature remains a hardware question, not a fabricated pass.

## Stage N: approved, backed-up Naomi comparison

**Diagnostic readiness gate.** Before a comparative hardware run, verify that the intended host console/log path produces a capture, that logs can be preserved before overwrite, and that base/configured ROM, configuration, manifest and matching ELF identities are retained together. Decide how the planned memory-soak test will observe Naomi heap/texture allocation trends. If the available emulator/debugger cannot expose them and no separately reviewed telemetry exists, mark memory acceptance **unavailable/pending**, scope minimal instrumentation separately, and do not claim a leak-free soak from stable Pi RSS or a responsive screen. Manual timings, visual captures and logs can still support basic rendering/control-flow checks; missing heap telemetry does not prevent those bounded checks. Diagnostic setup or instrumentation is not implemented by this documentation change.

**N0 — reviewable test package.** Read the active session's authorization and [live-system boundaries](../AGENTS.md#live-system-boundaries). Compare relevant installed host files with this checkout before proposing deployment. Provide the exact files/launch arguments to change, original and candidate hashes, owners/modes, test cases and rollback commands/paths. Prefer an isolated candidate selected with the host's existing `--exe` option if the inspected launcher permits it, rather than overwriting all original variants; the actual launch path must be reviewed. Scope settings and SRAM writes explicitly. Do not replace the installed package from this older public source tree.

**N1 — backup and observation baseline.** With no transfer/configuration edit active, back up affected host/menu files, selected original binary plus dark/light variants, relevant menu/catalog/NetDIMM settings and SRAM saves privately; record owners/modes. Verify archive contents/checksum and that the restoration procedure targets the correct files. Record what was backed up and where privately. Capture the unchanged working menu's controls, selection/settings behavior, payload/upload/startup times and CRT appearance using the same test IDs/flags. Obtain approval for the concrete comparison if not already authorized; obtain explicit user coordination for any startup, reboot, shutdown or cabinet-power test. A game launch is an action in the agreed case list, not a way to inspect a page.

**N2 — native text comparison.** Install/select only the reviewed candidate with rollback ready, no competing sender and no active edits. Check real physical JVS short Start launch, long Start settings, Back and both save/exit paths, repeat navigation, correct game/ID association, orientation and font readability at normal cabinet distance. Confirm only the intended selected game launches and reaches user-confirmed playable gameplay. Measure menu upload, any unpack/decompression, usable-menu time, selection-to-sender-start and selection-to-playable time separately with defined start/end events. Capture Naomi error codes/screens verbatim.

**N3 — SRAM.** Only within the approved write scope, verify backup-on startup associates the full 32 KiB snapshot with the previously played game, and restoration occurs before the next appropriate game. Compare private backup/hash evidence and user-observed state, not logs alone. Verify disabled SRAM does not write/restore; toggling backup on affects snapshots on the next menu startup. Preserve pre-test SRAM for rollback. Do not deliberately corrupt the live SRAM or send malformed restores; those remain fixture tests.

**N4 — controls, soak and startup.** Run the agreed repetition/soak and record the actual duration/cycles and available metrics. Observe CRT readability, overscan, blanking/click counts and signal loss/return without altering reset timing or NOW LOADING. A 31 kHz sync-reacquisition theory is not a chassis diagnosis. Test Single Boot/default OSM startup only in the separately coordinated window; retain custom entries and optional control/card behavior. Stop and roll back on regression rather than continuing unrelated enhancements.

**N5 — separate phone acceptance.** Follow [loading-status deployment/rollback](loading-status.md#deployment-and-acceptance--not-yet-performed) in a separate change/run. Install helpers before callers and back up/restore the related files together. Test one normal launch, duplicate requests following the one active upload, a subsequent different game, live 0% waiting and OSM-to-phone switching only after the OSM transfer finishes. Refresh/poll/retry must stay read-only. `COMPLETE` progress is not success until sender exit, and sender exit is not proof of gameplay. Never intentionally fail a real upload for this test; use fake-sender fixtures. Record phone status acceptance separately from native acceptance.

Exit record: retain the selected binary/host hashes, accepted/rolled-back state, residual risks, evidence IDs and next action. Verify rollback restored the reviewed original hashes/owners/modes if used. If any case was not run (especially Single Boot, SRAM or soak), record it explicitly; do not call the entire cabinet baseline accepted.

## Diagnostic sources that actually exist

These are source-inspected facilities, not a promise that a new telemetry collector is installed. Confirm the running version and availability in the test environment. Many logs are truncated on the next launch; copy them before retrying/restarting. Use a private timestamped run directory, with permissions appropriate to captured settings/addresses. Never commit raw captures, real ROMs/BIOS, SRAM, private addresses or cabinet media. `native/out/runtime-tests/` is ignored for local evidence; a directory outside the checkout is also suitable.

| Evidence | Existing source/path and limits |
| --- | --- |
| Build identity | `native/out/netbootmenu.bin`, `naomi.elf`, `SHA256SUMS`, `manifest.json`, compiler/ELF/package/image-ID text files. Preserve together; host-configured ROM has another hash. |
| Native console | `main.c` calls `message_stdio_redirect_init()`; parser/SRAM/packet failures use `printf`. The host receives `MESSAGE_HOST_STDOUT`/`STDERR` and logs them. This needs a working bridge/NetDIMM message path; without it no native console capture is guaranteed. `--verbose` adds host packet type/length/timing diagnostics. |
| Existing optional frame overlay | Host `--debug-mode` sets `enable_debug`; `main.c` displays instantaneous FPS, resolution and microseconds for draw submission. Capture it visually if enabled/supported. It is not a persistent frame-time history or complete GPU/input-latency measurement. |
| Native OSM host logs | `/var/log/netdimm_menu.log`, `/var/log/menulauncher.log`; both configured with `filemode='w'`. Capture before another menu invocation. `/var/log/menudump.bin` is the host-configured menu payload and can contain real catalog/settings; retain privately only. |
| Ordinary phone sender/loader | `/var/log/wipiloader.log`, `/var/log/netdimm_send.log`, legacy `/var/log/progress_<IP>`. The loader/sender logs are overwritten on launches; sender log is shared. Identify the run/target and capture promptly. An OSM path need not create the ordinary loader's job JSON. |
| Phone status job | `/run/wipi/upload-<target hash>.json` when the new status helper is installed; atomically replaced per target, volatile across reboot. Capture job ID, PID/start ticks, timestamps, progress baseline and terminal `state`/`detail` before a later job replaces it. There is no dedicated numeric sender-exit-code field: retain a numeric status only if an exposed log/detail supplies it, otherwise mark unavailable. The record is not present on the current cabinet merely because PR #1 merged. |
| Optional integrations | `/var/log/openjvs/openjvs.log` and `/var/log/openffb/openffb.log` only where enabled/available; collect on relevant control failures. Browser status/JSON response and console/network errors can distinguish a status-read failure from a stopped sender. Redact URLs/addresses/tokens. |
| Exceptions and visual faults | Emulator stdout/stderr/crash report, screenshots/video, Naomi error screen/code, PC/registers/backtrace if exposed, physical button sequence and host exit status. Include exact wording; do not infer a missing error code. |
| Memory and latency | Existing native host fixtures count exercised allocations/frees. No continuous Naomi heap/texture watermark or leak logger exists. Record emulator/debugger memory data only if supported, with tool/units/sample method. Pi process RSS measures the Pi process, not Naomi heap/texture memory; flat RSS cannot prove a leak-free menu. Use timestamped video for approximate input/startup/blanking timings and label resolution/uncertainty. Mark unavailable measurements explicitly. |

For every failure, capture the pre-failure state, exact timestamped input sequence (including Start hold duration), expected/actual outcome, relevant log interval, screenshot/video and error/exit code before another attempt. Record reproducibility as failures/attempts, earliest known passing build and whether rollback restores behavior. Change one factor at a time, keep fixture fault injection away from live targets and do not automatically retry a launch while gathering evidence. A missing log is a diagnostic gap to record, not proof of success.

### Own-board BIOS capture and explicit original-menu return (2026-11-13)

The [dedicated helper/capture client](../native/biosdump/README.md) has an offline cross-build and six synthetic protocol/output/deadline checks. After explicit user approval and verified private backups, the helper transferred/reset once. Capture completed exit 0 in approximately 27 minutes 18 seconds: two full volatile 2 MiB reads were byte-identical. The copied local private file matched the capture SHA-256 and Flycast's known BIOS CRC table recognized it. Firmware bytes, identity/hash and private addresses remain outside tracked source.

Preflight found Checking network, no active sender/menu host and target SRAM saving already false. The existing `/opt/wipi64-venv/bin/python` plus inherited PATH supplied dependencies. After capture, the original shipped menu transferred/reset once through installed `netdimm_menu`, using an exact settings clone with SRAM still false. Host evidence recorded length `000d8b38` and waiting for ROM selection. Installed CSV/settings/menu binary hashes remained unchanged and SRAM directory contained README only. The native candidate was not deployed. CRT was off; visual return and physical EEPROM/SRAM invariance remain unverified. Host file hashes do not prove physical settings invariance.

Two local Flycast launch attempts (default JIT and transient `config:Dynarec.Enabled=no`) exited 133 before BIOS/ROM load at `Sh4Recompiler::Init`, `core/hw/sh4/dyna/driver.cpp:349`: the RAM/context virtual-memory-layout assertion failed. Source inspection shows runtime interpreter selection still initializes the compiled recompiler first, so that option cannot avoid this startup assertion. No assertion was removed. A separate compile-time supported `TARGET_NO_REC` interpreter-only fallback built exit 0 with GDB disabled (the GDB-enabled combination failed linking dynarec-only `GetRegPtr`); [recipe and binary identity](flycast-local-build.md#supported-interpreter-only-fallback-after-startup-failure) preserve this build proof. The fallback subsequently loaded the private BIOS and synthetic configured ROM, rendered the list, accepted Up/Down and scrolled to the final title; it quit with exit 0. See the [bounded result and remaining cases](results/2026-11-13-native-emulator.md). E3 remains unsupported on stock raw ROM; no emulator bridge or menu semantic change was implemented.

The restored menu settings clone was subsequently preserved as evidence and its temporary path atomically aliased to the unchanged original installed YAML. This allows ordinary future UI settings edits to persist normally without another transfer/reset. It does not prove physical EEPROM/SRAM invariance.

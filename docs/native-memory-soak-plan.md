## First deliverable: offline diagnostic readiness

1. Confirm allocator reporting in the pinned build environment. Pinned libnaomi `c840eb85384725182392ee3361706e80ae4ca4c0` exposes `ta_texture_mallinfo()` in `libnaomi/naomi/ta.h`; `libnaomi/texture.c` reports `arena`, `uordblks` and `fordblks` while locking its allocator. It reports only allocations managed by that texture allocator; an all-zero result before allocator initialization is unavailable data, not evidence of zero use. Verify ordinary heap `mallinfo()` declaration, link/runtime behavior and field meanings against the actual toolchain before depending on it; source availability of the texture API does not prove usable heap telemetry.
2. Propose the smallest diagnostic-only change, reusing the isolated-copy approach of the [event diagnostic builder](../native/emulator/build-start-event-diagnostic.py). Record build/source patch, base/configured ROM and matching ELF identities separately. Do not replace or repin the canonical `45ef4f20…` artifact, install a new allocator, change rendering/input semantics or add a permanent overlay.
3. Collect bounded samples at defined stable states: after warmed main-menu rendering, after settings entry and after discard back to the same main-list entry. Record sample/cycle/state IDs, guest elapsed time, heap and texture used/free/arena values with units and API provenance. Take snapshots at the completed-frame loop boundary after `video_display_on_vblank()` and existing frame/profile accounting, not inside rendering or a partial transition. Trigger transition samples only after the intended screen has settled for a predefined number of completed frames and cleanup/message work has reached its documented quiescent point; determine that settling rule in offline readiness before execution. Read allocator counters before formatting/queuing diagnostic output. Idle may use a sparse guest timer. Keep collection/output bounded, avoid per-frame logging, and account for diagnostic/message-buffer allocations and dropped/queued records. Avoid logging during a held Start or settings decision. Before the next Start, require host confirmation that the post-discard sample arrived; use existing capture, not an on-screen overlay. Report host and guest elapsed times separately, without converting them or deriving input latency. Instrumentation can still affect timing: do not use this run as canonical input/performance acceptance.
4. Prove the diagnostic builds and emitted records can be captured and decoded offline, without a sender. Use only checks relevant to the changed native/capture paths; retain focused ownership tests/sanitizers where affected. Emulator synthetic rendering/navigation can verify basic collection, but the stock raw-ROM path still lacks settings-message support. Do not invent emulator settings-cycle evidence or infer target totals from host counters.

Exit package: reviewed concrete diff, metric definitions/limitations, bounded capture/sample policy, isolated build/ELF identities and focused offline proof. If trustworthy target heap or texture data cannot be collected, mark the corresponding memory gate unavailable/pending and resolve that gap before claiming a memory soak. Stable Pi RSS is not a substitute. **The offline package is now implemented and checked; see the [diagnostic use/metric limits](../native/diagnostics/README.md). Proposed bounded cases, subject to successful offline readiness and final review:

| Case | Procedure | Evidence |
| --- | --- | --- |
| Warm-up | Traverse the same list/title set; open/discard the agreed standard game's settings twice, without changing values | Establish font/glyph/cache and diagnostic warm-up; retain its growth separately from measured repetitions |
| Repetition | 20 open/discard cycles for that same game, in four batches of five | Hold Start until settings appear, release, verify literal **go back to main menu without saving**, activate once; compare metrics at the same stable main-menu state after each cycle |
| Idle | Leave the warmed menu untouched for 15 minutes, with sparse bounded samples | Actual host elapsed duration plus guest time, input responsiveness before/after, readable/animating screen, allocator trend and communication errors |
| Return | Preserve captures, stop only the current verified idle diagnostic host and confirm exit, then restore the original through the installed normal host | Exact clone/real-YAML and stable installed-file checks, SRAM directory unchanged, verified original payload/host waiting and user-confirmed Up/Down |

The initial two warm-up cycles are a proposal, not proof that every cache has stabilized. Repeat only the same title/setting/content set during the measured block; document legitimate bounded cache growth and allocator arena retention. Do not hide continued growth by extending warm-up indefinitely. If warming cannot be distinguished from a persistent allocation trend, stop and investigate rather than awarding a pass. Preserve sample ordering and compare equivalent states after cleanup/quiescence, not settings-open allocations against a closed-menu baseline.

## Acceptance and stop rules

- Require complete usable samples and successful source/capture ownership checks. Report visual stability, protocol behavior, heap trend and texture trend as separate outcomes. Use verified `uordblks` as live allocated block bytes at equivalent post-cleanup states. `arena`/`fordblks` describe allocator extent/free-space context and do not establish fragmentation or exact total resource consumption. Apply the heap equivalent only after its API/semantics are verified; otherwise heap acceptance stays pending. Predeclare a trend flag: positive net live-use growth across every one of the four five-cycle batches after warm-up requires investigation, not PASS. Any other unexplained persistent increase also remains unresolved; a pattern need not meet that flag to be a defect. Explain bounded cache/plateau allowances from measured evidence before the run rather than inventing a byte tolerance or adjusting it afterward. Retained arena/high-water growth alone is not a leak.
- A bounded pass means no leak detected in these exercised paths/duration, not “leak-free.” Totals do not identify fragmentation, all allocation failures or memory outside the measured allocators; record those coverage limits. Diagnostic observer cost must be disclosed.
- Stop inputs on wrong entry, unexpected selection/save/config/SRAM message, parser/allocator fault, missing/truncated telemetry, monotonic unexplained growth, freeze, corruption or loss of controls. Preserve exact samples/logs/errors. No automatic retry, game launch, power action or forced live failure; return only under the approved safe recovery once no transfer is active.
- Menu startup still clears/writes physical EEPROM. SRAM backup OFF does not establish physical state invariance. File backup and original return do not restore physical EEPROM/SRAM. No claim of that rollback, cold-host saved-settings persistence, Single Boot or real SRAM restore follows from B4.

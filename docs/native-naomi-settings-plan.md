## B1 permitted controls and expected exchange

1. Upload the verified bare candidate through the reviewed installed host once. Preserve its generated configured dump/hash and check SRAM flag OFF, current catalog association and candidate source/ELF identity. Record upload completion and user-visible usable menu separately.
2. Use only the necessary Up/Down input to highlight the pre-agreed catalog entry. No short Start tap on the main list. Press and **keep Start held until the settings/loading transition is visibly entered before releasing**. Do not release based on a one-second wall timer. Expected native request is `0x1001` with the four-byte selected index, host ACK `0x1002` with matching index, and settings data `0x1005`; require the actual settings screen for the correct game, not only “Fetching game settings...” or an ACK.
3. If the transition is absent or uncertain, keep Start held. Stop only the explicitly verified candidate host while still held, confirm it exited, then release and coordinate the approved original return. Do not blindly release/retry with a host accepting selections. Preserve evidence first; no additional candidate attempt is included.
4. Once settings are visibly entered and Start is released, use Up/Down only to highlight the literal action **“go back to main menu without saving”**, visually confirming the full label before pressing Start once to activate it. This is the game-settings action at menu action index 2 in `screens.c`; it sets the selected game and returns to the main list without sending settings or selection. Do not activate “save and launch game” or “save and go back to main menu”. **Route (Claude review, source-checked 2026-11-13):** the settings cursor starts on the first row and Up does not wrap, so the only route is repeated Down. The three actions are the last three rows in the order launch, save, discard, so the cursor passes over both save actions on the way; passing over them sends nothing, but Start on “save and launch game” starts a real game transfer. Press Down until the cursor no longer moves; the last row is the discard action. Keep hands off Start until that full label is highlighted. Start on an earlier patch row only toggles it locally, and the discard action drops that change. Releasing the held Start inside the settings screen does nothing, because that screen acts only on a new Start press. Do not use Left/Right, toggle a patch/force-settings value, or edit any displayed setting. Test/Service are excluded; neither is assumed to mean Back.
5. Confirm the main list returns to the same entry with usable directional controls. Preserve candidate host log/console, message evidence, screenshots/operator notes, generated dump and clone before any original return. Verify that no `0x1000` selection, `0x1007` settings save, `0x1003` configuration save or SRAM exchange was observed in complete, verified host capture; this cannot prove the guest never queued an undelivered packet; verify the clone is byte-for-byte unchanged. Any missing packet evidence is an unverified assertion, not a pass.
6. Stop only the verified candidate host after confirming no transfer is active, then perform the one approved original-menu upload/reset using the installed original menu and normal real settings, without candidate `--exe`, clone or debug arguments. Confirm successful transfer, host waiting for selection and user-visible original menu/JVS controls. Retain normal original host as appropriate to the approved return; verify its actual process state rather than claiming it in advance.

Local source references: `game_settings_load` sends `0x1001`, checks ACK index and rejects mismatched settings data; `game_settings` action 2 returns without saving, action 0 sends settings **and** selection, action 1 sends settings; `protocol.h` defines the message IDs. ## Stop, restoration and acceptance limits

Stop on unexpected selection/save/config/SRAM packet, wrong game association, timeout/error, uncertain transition, input/render freeze, unexpected clone/file change, transfer failure or cabinet behavior. Preserve evidence before any retry; no retry or additional transfer is automatic. A selection already accepted can initiate a real game transfer, so do not claim stopping the host reverses it. Reassess the concrete recovery before any action beyond the approved original return. Never kill by broad process name.

The native candidate reads EEPROM, clears its game-settings size and calls `eeprom_write()` on startup. SRAM OFF does not suppress that write. BIOS boot/original return can also affect physical state. No supported live physical EEPROM snapshot/restore was verified; file backups and original-menu return cannot prove or restore physical EEPROM/SRAM invariance. SRAM OFF suppresses the candidate snapshot sender, but the host can write a valid received SRAM snapshot regardless of its flag: OFF is not a host write guard. No SRAM enable/restore, Test/Service/configuration, optional debug, game selection, save, phone launch, control/card setup, Single Boot or startup/default change belongs to B1.

After return, compare installed non-log files' hashes/numeric owners/modes, real YAML, clone and SRAM directory to fresh preflight. Record any differences and exact process outcome privately. B1 success requires correct settings fetch/display plus literal discard/Back, no forbidden messages observed in complete verified host capture, unchanged clone and confirmed original return. It does not establish saving, game boot, SRAM, memory/texture soak, exact physical JVS threshold or full baseline acceptance.

# Ordered roadmap and acceptance gates

Read [the AI handoff](ai-handoff.md) for the dated source/artifact snapshot and current proof. This file owns work order and gates; implementation details remain in the linked documents. A source merge, a host test, an emulator result and a cabinet observation are different kinds of evidence.

| Order | Milestone | Required result before moving on |
| --- | --- | --- |
| 0 | Preserve the working cabinet and identify the candidate | Keep the cabinet-tested OSM-save fix and ordinary-upload guard, Single Boot and the installed original menu binaries. Match candidate source, base ROM and any configured runtime ROM to their hashes. |
| 1 | Prepare an isolated native emulator test | Inventory a suitable emulator and its supported Naomi homebrew/input/host-message features; use a lawfully available BIOS if required. The [offline synthetic fixture generator](../native/README.md#offline-emulator-fixture) and configured ROM now pass layout/identity checks. Own-board BIOS capture and local Flycast setup are now complete. The interpreter-only build has [basic rendering/navigation evidence](results/2026-11-13-native-emulator.md); the stock raw-BIN route lacks host-message support, so E3 remains unsupported and can be scoped for real NetDIMM testing rather than requiring a new emulator bridge. |
| 2 | Establish the native text baseline in the emulator | Record rendering, fonts, navigation and repeat behavior; exercise short Start, long Start/settings, Back and save/load only where an isolated message bridge supports them. Record unsupported paths as unverified. Resolve reproducible failures with captured evidence before a cabinet comparison. |
| 3 | Prepare and obtain approval for a backed-up Naomi comparison | Compare relevant installed files, produce the exact file/launch diff, verify backup and rollback, choose game IDs and test order, and agree the physical test window. Verify console/log capture and the matching ROM/config/ELF bundle; decide how memory trends will be observed or record that acceptance test pending. Then test physical JVS, real video/CRT, settings, SRAM association/restore and game launch. Startup/Single Boot tests need explicit user coordination. |
| 4 (independent track) | Accept the phone loading-status enhancement separately | This can run before or after the native comparison in its own approved window. PR #1 source is merged but its new status screen is not installed or cabinet-accepted. Follow its [deployment plan](loading-status.md#deployment-and-acceptance--not-yet-performed), capture the normal/busy/subsequent-game/OSM-to-phone results, and coordinate Single Boot. Keep this rollout separate from the native-menu comparison so failures can be attributed. |
| 5 | Build a five-game still-artwork proof | Only after the native baseline and loading-status gates: add bounded/versioned payload parsing, correct selection IDs, missing/corrupt-art fallback and a text fallback. Measure payload, startup, navigation and memory cost; check emulator behavior, then an approved backed-up cabinet comparison before expanding the catalog. |
| 6 | Evaluate details and optional video | Reuse catalog metadata; establish a readable still-image/details view first. Follow the [CRT/performance experiment](illustrated-osm-investigation.md#post-baseline-check-game-details-video-and-crt-experience). Agree numerical budgets from measured baselines before adopting video. Keep immediate Launch/Back and still fallback; defer video if it adds noticeable delay or fails the budget. |
| Later | Scope other product changes individually | Optional phone launcher (artwork/favourites/recent/details), search and touch filters, bulk list enable/disable with atomic CSV updates, selective catalog/art corrections and theme polish. None is a wholesale replacement approval. The [CRT clicking investigation](crt-sync-follow-up.md) remains a separate controlled comparison. |

Milestones 1–3 are the ordered native track; milestone 4 is the independent phone track. Native emulator preparation can proceed while phone deployment awaits a hardware window, and phone acceptance need not wait for native acceptance. The next concrete native task is milestone 1, not artwork or video. Emulator success cannot close real JVS, NetDIMM, battery SRAM, CRT or Single Boot acceptance.

Every runtime run uses [the test plan](native-runtime-test-plan.md) and a copy of [the result/bug template](templates/runtime-test-result.md). Record pass/fail/blocked/not run/unavailable per case, evidence references and unresolved bugs. A blocker does not become a pass because a later task is attractive. When a gate closes, update the dated state in [the handoff](ai-handoff.md), retain evidence references and identify the next open gate.

Preserve physical short-Start launch and long-Start settings, the five-second OpenFFB delay, optional control/card support and current reset/NOW LOADING behavior. Browsing must not launch a game. The ordinary-upload lock does not coordinate independent OSM/standalone transfers: finish the OSM transfer before a phone launch. No reboot, startup test, game launch or deployment is implied by this roadmap alone; use the authorization already present in the active session and coordinate additional live actions as described in [AGENTS](../AGENTS.md#live-system-boundaries).

Selective references remain [WiPiNetbooter-NG](https://github.com/metisnc/WiPiNetbooter-NG/tree/23412c084e5fc19d920308f4a2d1566c59181ce2), [thegoodguys80](https://github.com/thegoodguys80/WiPiNetbooter/tree/38fb4d42cadbde53ddb2d9c4639a84c6b6fafa13) and [AyanamiRei1](https://github.com/AyanamiRei1/WiPiNetbooter/tree/03282df71e0cf12a1361cbdc748f7b2f12008c77). Review individual assets/rows/code for compatibility; do not adopt their complete backends, configuration writers or images without separate review.
